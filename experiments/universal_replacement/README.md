# 添付画像の5企業・8労働者問題の universal-replacement 安定性全探索

この実験は画像の**固定された1問題**について、全員未マッチを含むすべての実現可能な
個人合理的マッチングを列挙し、既存の `Matching::is_universal_replacement_stable` で判定する。
選好プロファイル全体を列挙する実験ではない。

初回のコード作成後、全マッチング探索と2つの改良DAの全選択経路探索を実行済み。
以下の「事前見積もり」は実行前の記録。最新の実測結果は末尾を参照。

## 画像から転記した問題

定員は `(2,2,2,2,1)`。コードの元データは [problem_5x8.hpp](problem_5x8.hpp) にあり、
転記部分は画像と同じ1始まりの番号を使う。以下の順序は左から好ましい順。

| 企業 | 労働者への選好 |
|---|---|
| f1 | w2 > w6 > w7 > w1 > w5 > w8 > w3 |
| f2 | w3 > w1 > w6 > w2 > w7 > w4 |
| f3 | w7 > w4 > w2 > w5 > w1 > w3 > w6 |
| f4 | w6 > w7 > w4 |
| f5 | w8 > w1 > w4 > w3 |

| 労働者 | 企業への選好 |
|---|---|
| w1 | f1 > f3 > f2 > f5 |
| w2 | f2 > f1 > f3 |
| w3 | f3 > f2 > f5 > f1 |
| w4 | f2 > f3 > f4 > f5 |
| w5 | f1 > f3 |
| w6 | f3 > f2 > f1 > f4 |
| w7 | f2 > f1 > f3 > f4 |
| w8 | f1 > f5 |

共通禁止ペア（対称）は次の9組。

```
{w2,w3}, {w2,w6}, {w2,w8}, {w3,w5}, {w4,w5},
{w5,w7}, {w5,w8}, {w6,w8}, {w7,w8}
```

リストに載っていない相手は受け入れ不可とする。長さ `k` のリストを `k,k-1,...,1` の
正のスコアに変換し、未掲載相手は `-INF`、未マッチは `0`。
禁止同僚ペアは両方向を `-INF`、それ以外は `0`。
今回の安定性は序数比較だけを使うため、正のスコアの間隔は結果に影響しない。

## 安定性と全探索の範囲

各労働者について「未マッチ」または「双方が受け入れ可能な企業」を選ぶ深さ優先探索。
定員超過・受け入れ不可・禁止同僚ペアを含む枝をその場で除く。
今回のデータは正のスコアが最大7、拒否が `-100000` なので、受け入れ不可の割当を
合計スコアで補うことはできない。この枝刈りで個人合理的な解を失うことはない。
各許容マッチングを重複なく1回ずつ判定し、最初の安定解を見つけても探索を止めない。
`Matching` はスコアをキャッシュするため、候補ごとに新しいオブジェクトを作る。

安定性は「現状がfeasibleかつ個人合理的で、universal-replacement blocking pairがない」。
空席への追加ブロッキングは含まない。全定員が正なので、全員未マッチは常にこの条件を満たす。
したがって、未マッチを許す場合の**存在そのものは探索せずにYESと分かる**。
全探索では、安定解の全件数・人数別の件数・最大マッチ人数・8人全員がマッチする安定解の有無を調べる。
実行結果では、23,521候補中4,791件が安定、8人全員がマッチする安定解は21件だった。

## ビルドと実行コマンド

`programs` ディレクトリからビルド：

```sh
cmake -S . -B build
cmake --build build --target exhaustive_universal_replacement_5x8 -j4
```

以下は今後実行するときのコマンド。コード作成時には実行していない。

```sh
./build/experiments/universal_replacement/exhaustive_universal_replacement_5x8
```

全員マッチの安定解の有無を主に見る場合：

```sh
./build/experiments/universal_replacement/exhaustive_universal_replacement_5x8 --min-matched 8
```

オプション：

- `--min-matched 0..8`：存在判定とCSVへの出力対象の最低マッチ人数（既定0）。
  全探索自体と人数別の集計は常に全候補を対象とする。
- `--output DIR`：出力先の親ディレクトリ（既定 `experiments/universal_replacement/outputs`）。
- `--help`：使用方法。

実行ごとに `run_<Unixミリ秒>[_suffix]` ディレクトリを作成し、既存結果を上書きしない。

| 出力 | 内容 |
|---|---|
| `problem.txt` | 元の選好順序・定員・禁止ペア |
| `summary.txt` | 全探索の完了、判定件数、安定解の総数と人数別の件数、人数別の最初の解、実測秒数 |
| `stable_matchings.csv` | 最低マッチ人数を満たす全安定解。列w1..w8は `f1`..`f5` または `unmatched` |

`candidate_index` は枝刈り後の候補に付ける1始まりの番号。
2つの改良DAはこの実験では呼び出さず、今後の比較用に元の選好を保持する。

## 計算時間の事前見積もり（探索未実行）

候補数は実際の安定性探索を実行せず、組合せ式から計算できる。

| 条件 | 候補数・上限 |
|---|---:|
| 各労働者が5企業または未マッチを選ぶ | `6^8 = 1,679,616` |
| 定員だけを守る | `393,161` |
| 双方受け入れ可能な相手または未マッチを選ぶ（定員・禁止ペアは未反映） | `5×4×5×5×3×5×5×3 = 112,500` |
| このコードが実際に安定性を判定する | `112,500` 以下。定員・禁止ペアの枝刈りでさらに減少 |

定員だけを守る候補数は、企業への割当人数を `k1..k5` として
`sum 8! / ((8 - sum ki)! * product ki!)`（`0 <= ki <= qi`, `sum ki <= 8`）で求めた。
実行後に確認した枝刈り後の候補数は23,521件。

既存の3企業・5労働者の実験は、各18,432問題・456候補、計8,404,992候補を評価している。

| 参照ログ | 実測全体時間 | 候補1件あたりの全体時間換算 |
|---|---:|---:|
| [線形スコア](../stability_simulation/outputs/run_20260907_223836_seed20260902/3x5/summary.txt) | 1,126.241498秒 | 約134マイクロ秒 |
| [超増加スコア](../stability_simulation/outputs/run_20260930_161902_seed20260902_firmsuperincreasing/3x5/summary.txt) | 784.587957秒 | 約93.3マイクロ秒 |

この単価を候補数の上限112,500にそのまま掛けると **約10.5〜15.1秒**。
これは以前の全体時間（旧安定性2種類の判定・アルゴリズム実行・生成・出力を含む）を
候補数で割った換算値であり、新しい判定そのもののベンチマークではない。

新しい問題は5企業・8労働者で1件の処理が大きくなる一方、
今回の判定は1種類で、定員は最大2、禁止ペアで枝刈りできる。
本ターゲットはOpenMPを有効にせず、候補ごとに並列領域を作る費用も避ける。
これらを考慮した同程度の環境での暫定予測は **数秒〜1分程度**、余裕を見るなら数分。
これは実測値でも厳密な時間上限でもない。ビルド時間は含めない。
実際の秒数は各実行の `summary.txt` に記録する。初回の全マッチング探索は0.118966秒だった。

## 改良DAのランダム選択の全探索

2つの改良DAの各ランダム操作（拒否ペアの処理順・削除する個人）を直接分岐させ、
各経路の最終マッチングを**元の選好**で判定する正式な調査コードは
[exhaustive_da_paths.cpp](exhaustive_da_paths.cpp)。通常のDA本体を呼び出し、
任意指定できる `DARandomChoiceSelector` でランダム選択を制御する。
selectorを省略した既存の呼び出しでは、従来の乱択の挙動を維持する。

```sh
cmake -S . -B build
cmake --build build --target exhaustive_da_paths_5x8 -j4
./build/experiments/universal_replacement/exhaustive_da_paths_5x8
```

`--output DIR` で出力の親ディレクトリを指定できる。
実行ごとに `outputs/da_paths_<Unixミリ秒>[_suffix]` を作成する。

- `summary.txt`：全経路数、安定・不安定の経路数、重複を除く最終結果、仮説判定、実測時間。
- `problem.json`：この実行で使用した定員・元の全選好行列・順位リスト。
- `firm_paths.csv` / `worker_paths.csv`：全経路について削除履歴、最終マッチング、安定性、blocking pair。
- `firm_paths.jsonl` / `worker_paths.jsonl`：各選択のラウンド、選択肢、選択結果、選択前のマッチングを含む詳細。

CSVの削除履歴 `r4:f2:w6` は「第4ラウンドに企業f2からw6を削除」の意味。
JSONの企業・個人は1始まり。割当ベクトルはw1..w8の順で、`0` は未マッチ、`1..5` は企業。
選択肢のインデックスだけは0始まりで、削除対象の `0` はleft、`1` はright。
ペア順序の選択では、残る全ペアから次に処理するものを選び、全順列を網羅する。
片方が既に削除されたペアには削除対象の選択肢を発生させず、スキップする。

探索は意思決定の列の未指定部分に達するたび、全選択肢に分岐してDAを初期状態から再生する。
最初の安定解で停止せず、同じ最終マッチングに至る別経路も保存する。
乱数seedをサンプリングする方法ではない。経路数の比は成功確率として扱わない。

検証する仮説は「worker/doctor proposingには安定解に到達する経路が一つもなく、
firm proposingには少なくとも一つ存在する」。この固定問題・現在の仕様について判定する。

### 2026年10月7日の実行結果

全選択経路を実行し、firm側3/3経路、doctor/worker側8/10経路が安定だった。
仮説の「doctor側には安定になる経路が存在しない」は成立しない。
全ケース・反例・不安定な2経路のblocking pairは
[結果レポート](recorded_results/da_paths_1791356176635/report_ja.md) に記録した。

独立したPython実装で元の選好から全ケースの安定性、分岐網羅性、CSV/JSONLの一致を検算できる。

```sh
python3 experiments/universal_replacement/verify_da_paths.py experiments/universal_replacement/recorded_results/da_paths_1791356176635
```

### 全経路のMermaid図とラウンド詳細

[全体分岐図と経路一覧](da_paths_index.md) から、
firmの3経路、doctorの10経路それぞれの独立したMarkdownに移動できる。
全経路について提案、A・B前後のマッチング、禁止ペアと2択、永久削除、残る提案先、停止理由を記録した。

図の生成時には、C++を呼ばない別実装のPythonモデルから全ラウンドと全分岐を再計算する。
全選択履歴・選択時点のマッチング・最終割当が保存済みC++結果と完全一致した場合にのみ出力する。

```sh
python3 experiments/universal_replacement/render_da_paths.py experiments/universal_replacement/recorded_results/da_paths_1791356176635
```

Markdownはこの実験ディレクトリ直下の `da_paths_index.md`、`firm_path_01.md`〜`03.md`、
`worker_path_01.md`〜`10.md` に保存する。
JSONは実行結果ディレクトリ内の `path_details/verification.json` と `*_round_traces.json` に保存する。
